1. Objet et périmètre du projet
Le projet consiste à développer une plateforme de contrôle interne permettant de gérer les fournisseurs, les transactions
fournisseurs et les constats d’audit associés. Lorsqu’un constat est créé, un événement métier est publié puis consommé
par un service de notification chargé d’envoyer un email de test. L’application est construite avec une architecture
microservices basée sur Java, Spring Boot et Spring Cloud.
Priorité : satisfaire et démontrer les exigences de la grille officielle, jalon par jalon. Les fonctionnalités avancées d’analyse
d’anomalies sont reportées après validation du socle évalué.
2. Objectifs mesurables
• Documenter l’architecture globale, les classes de chaque service et les références entre services.
• Fournir des CRUD autonomes, avec DTO, validation des entrées et base de données isolée par service métier.
• Enregistrer les instances dans Eureka et faire passer les requêtes par la Gateway.
• Externaliser les configurations dans Config Server et prouver qu’elles sont effectivement chargées.
• Vérifier les références distantes par OpenFeign et exposer des consultations enrichies.
• Démontrer le cycle complet d’un événement RabbitMQ jusqu’à l’email visible dans MailHog.
• Démontrer les mécanismes de résilience, de limitation de débit, de gestion d’erreurs et d’idempotence prévus au jalon
V6.
• Livrer une collection Postman versionnée qui permet de rejouer les scénarios et leurs cas d’erreur.

5. Exigences et critères d’acceptation par jalon
V0 — Conception et documentation
• Un schéma global représente les services, les bases, Eureka, Config Server, Gateway, RabbitMQ et les flux
synchrones/asynchrones.
• Un diagramme de classes est fourni pour chaque microservice métier et explicite les références distantes (supplierId,
transactionId).
• README.md contient les prérequis, ports, variables, ordre de démarrage, commandes, endpoints et instructions
Postman.
• Acceptation : une personne extérieure peut lancer le socle en suivant le README.
V1 — Modèle métier et CRUD
• Les trois services métier disposent des opérations Create, Read, Update et Delete, plus consultation de liste et par
identifiant.
• Chaque service utilise sa propre base et ne consulte jamais directement la base d’un autre service.
• Les entrées sont validées avec Bean Validation ; les API exposent des DTO et un mapping dédié.
• Une collection Postman exportée contient les scénarios CRUD, les variables et des assertions de réponse.
V2 — Eureka Service Discovery
• Chaque instance s’enregistre auprès d’Eureka avec un spring.application.name cohérent.
• Le tableau de bord montre toutes les instances attendues avec le statut UP.
• Preuve : capture du dashboard et vérification des noms/états au moment de la démonstration.
V3 — Gateway et Config Server
• Les routes de la Gateway utilisent la découverte dynamique (lb://...) ou un routage statique avec équilibrage démontré,
selon la grille.
• Le load balancing est prouvé en lançant deux instances de supplier-service sur des ports différents.
• Les propriétés applicatives sont externalisées dans un dépôt de configuration ; chaque service charge le fichier
correspondant à son nom.
• Preuve : appels Postman via la Gateway, preuve des deux instances et endpoint du Config Server.
V4 — Communication synchrone OpenFeign
• transaction-service vérifie l’existence du fournisseur avant création ou modification d’une transaction.
• finding-service vérifie l’existence de la transaction avant création ou modification d’un constat.
• GET /transactions/{id}/details renvoie les données de transaction enrichies avec le fournisseur.
• GET /findings/{id}/details renvoie le constat, la transaction et le fournisseur dans un DTO composé.
• Les cas de référence inexistante renvoient une erreur explicite 404 ou 400 et sont testés avec Postman.
V5 — Broker et notification
• RabbitMQ comporte un exchange, une queue et un binding configurés et documentés.
• La création d’un constat publie FindingCreated avec findingId, transactionId, supplierName, severity, description et
createdAt.
• notification-service consomme l’événement et envoie un email via SMTP de test MailHog.
• Acceptation : la démonstration montre la requête Postman, le message reçu par RabbitMQ, sa consommation et l’email
dans MailHog.

V6 — Résilience, erreurs et idempotence
• Resilience4j Circuit Breaker et Retry sont appliqués à au moins deux appels Feign : transaction→supplier et
finding→transaction.
• Le rate limiting de la Gateway est configuré et un scénario Postman démontre une réponse 429.
• ControllerAdvice renvoie un format d’erreur homogène avec code, message, horodatage et chemin.
• Les créations sont idempotentes via Idempotency-Key ou une référence métier unique : une répétition ne crée pas de
doublon.
• Ce jalon est prévu dans le cahier des charges ; son poids exact dans la première note doit être confirmé auprès du
professeur.

7. Stack technique et exécution
• Langage et framework : Java 21, Spring Boot 3, Spring Data JPA, Bean Validation, MapStruct.
• Spring Cloud : Eureka Server, Config Server, Spring Cloud Gateway, OpenFeign, Resilience4j.
• Messagerie : RabbitMQ avec Spring AMQP.
• Bases : PostgreSQL, une base par service métier ; H2 peut être utilisé pour les tests.
• Rate limiting : Gateway RequestRateLimiter avec Redis.
• Email : Spring Mail et MailHog pour une démonstration locale sans envoi à de vrais destinataires.
• Qualité : Postman, JUnit 5 et Mockito.
• Infrastructure : Docker Compose pour les dépendances locales, selon les capacités de la machine.
8. Collection Postman : structure obligatoire
• V1-CRUD : scénarios positifs et négatifs pour chaque service métier.
• V2-Eureka : vérification manuelle documentée du statut UP de toutes les instances.
• V3-Gateway-Config : appels via Gateway, test de deux instances et vérification de la configuration chargée.
• V4-Feign : création avec référence valide, référence inexistante et endpoints /details.
• V5-Async : création d’un constat, puis vérification de l’événement et de l’email dans RabbitMQ/MailHog.
• V6-Resilience : service distant indisponible, retry/circuit breaker, réponse 429 et double soumission idempotente.
La collection utilise des variables d’environnement (baseUrl, IDs créés) et des tests automatiques sur les statuts HTTP et
les champs essentiels. Elle doit être exportée et versionnée avec le code.
9. Livrables à remettre
• Code source versionné avec un dossier par service et un dépôt de configuration identifiable.
• Schéma d’architecture global et diagrammes de classes par microservice.
• README complet : installation, prérequis, ports, configuration, ordre de démarrage, appels de test et dépannage.
• Collection Postman exportée avec variables et scénarios de test.
• Fichier Docker Compose pour les composants d’infrastructure pris en charge.
• Scénario de démonstration reproductible ; captures d’écran des preuves clés et vidéo de secours si nécessaire.
